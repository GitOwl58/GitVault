**[[Container|Containerization]]** packages and runs applications in isolated environments (containers, VMs, or serverless) via technologies like **[[Docker]]**, Docker Compose, and **[[LXC|Linux Containers]]**. Containers are lightweight, fast to deploy, and portable, isolating the host from whatever runs inside. That isolation is a security boundary, not an absolute one: methods exist to escalate privileges inside a container or escape it entirely, so containers still need hardening.

### Docker
**[[Docker]]** is an open-source platform for packaging applications as self-contained images run as containers, using a layered filesystem and resource isolation. Images come from **Docker Hub** (public or private repositories) or are built locally from a **Dockerfile**, which lists the steps needed to assemble the image (base image via `FROM`, package installs, user setup, exposed ports, startup command via `CMD`).

- `docker build -t <tag> .`: build an image from a Dockerfile in the current directory.
- `docker run -p <host_port>:<container_port> -d <image>`: run a container, mapping ports, `-d` for detached/background.

| Command | Purpose |
| --- | --- |
| `docker ps` | List running containers |
| `docker stop` / `docker start` / `docker restart` | Manage a container's run state |
| `docker rm` / `docker rmi` | Remove a container / an image |
| `docker logs` | View a container's logs |

Containers are designed to be immutable: runtime changes are lost when the container stops, and permanent changes require building a new image (a new Dockerfile `FROM` the original, with the desired edits, rebuilt and retagged). Production-scale management typically moves to Docker Compose or Kubernetes.

### Linux Containers
**[[LXC]]** virtualizes multiple isolated Linux systems on one host using kernel resource-isolation features (**cgroups**, **namespaces**), without Docker's application-centric tooling on top. Compared to Docker: LXC images are built manually (a root filesystem plus installed packages) rather than from a Dockerfile, are less portable, need more technical expertise, and offer somewhat less robust security by default; Docker trades some of that low-level control for a friendlier, more portable, more secure-by-default workflow.

- `sudo apt-get install lxc lxc-utils -y`: install.
- `sudo lxc-create -n <name> -t ubuntu`: create a container from a template.

| Command | Purpose |
| --- | --- |
| `lxc-ls` | List containers |
| `lxc-stop` / `lxc-start` / `lxc-restart -n <container>` | Manage run state |
| `lxc-attach -n <container>` | Connect to a container |
| `lxc-config -n <container> -s storage/network/security` | Manage container settings |

LXC hardening: restrict access, limit resources (via `lxc.cgroup.cpu.shares` and `lxc.cgroup.memory.limit_in_bytes` in `/usr/share/lxc/config/<container>.conf`, then `sudo systemctl restart lxc.service`), isolate from the host, enforce mandatory access control, keep containers updated. **Namespaces** are what make this isolation possible: each container gets its own PID space (process IDs isolated from the host), its own `net` namespace (network interfaces, routing, firewall rules), and its own `mnt` namespace (root filesystem), all separate from the host and from other containers, though namespaces alone are not a complete security guarantee.

Penetration-testing use cases: spinning up a disposable environment matching a target's dependency/version quirks, or a sandboxed environment to safely test exploits and malware.
