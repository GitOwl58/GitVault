Remote desktop protocols give graphical remote access, used for troubleshooting, upgrades, and administration. Windows favors **[[RDP]]**; Linux favors **[[VNC]]**, built on **X11**.

### XServer
**X11** (X Window System) is the protocol Linux GUIs run over: a collection of protocols/applications letting application windows render on a display. It's network-transparent: even a single-machine desktop talks to itself over the internal network via an X server, and is bundled with nearly every Ubuntu-derivative desktop install. It mainly runs over TCP/IP (ports ~TCP/6001-6009, with 6000 for the first display `:0`) but can also use Unix sockets. Because rendering happens on the *local* machine (unlike VNC/RDP, which render remotely and stream the output), X11 is efficient with bandwidth and remote-host load, but its major weakness is that X11 traffic is unencrypted by default. This is fixed by tunneling it over **[[SSH]]**: set `X11Forwarding yes` in `/etc/ssh/sshd_config`, then `ssh -X user@host /path/to/app` runs a remote GUI app locally.

![[X11 forwarding Firefox example.png]]

Without that protection, X11 is dangerous: a fully open X server lets anyone on the network read window contents, log keystrokes, move the mouse, or inject input, all invisibly to the user in front of the screen, using ordinary tools like `xwd`/`xgrabsc`. Real CVEs (CVE-2017-2624/2625/2626) let a local attacker exploit XServer bugs to run arbitrary code with user privileges.

### XDMCP
The **X Display Manager Control Protocol** lets an X Display Manager redirect a full remote GUI session (KDE, GNOME...) to a client over UDP port 177. It's insecure by design and shouldn't be used anywhere security matters; a classic risk is a man-in-the-middle attacker impersonating one side of the XDMCP session to hijack GUI access.

### VNC
**[[VNC]]** (Virtual Network Computing, based on the RFB protocol) is Linux's most common remote-desktop protocol: encrypted and authenticated by design, unlike bare X11. Two server models exist: sharing the host's actual live screen (like remote support), or hosting separate virtual sessions per login (like a terminal server). Common implementations: TigerVNC, TightVNC, RealVNC, UltraVNC, the latter two favored for stronger encryption. A VNC server listens on TCP 5900 for display 0, with additional displays on 590x (5901, 5902...).

Setting up TigerVNC (paired with XFCE4, since GNOME over VNC tends to be unstable):
```
sudo apt install xfce4 xfce4-goodies tigervnc-standalone-server -y
vncpasswd
touch ~/.vnc/xstartup ~/.vnc/config
chmod +x ~/.vnc/xstartup
vncserver
```
`~/.vnc/xstartup` controls how the session launches (`/usr/bin/startxfce4`); `~/.vnc/config` sets display options (geometry, dpi). `vncserver -list` shows active sessions, ports, and PIDs.

To secure the connection, tunnel it over **[[SSH]]** rather than exposing VNC directly: `ssh -L 5901:127.0.0.1:5901 -N -f -l user host`, then connect the viewer (e.g. `xtightvncviewer localhost:5901`) through the tunnel.
