### Windows Domains
A **[[Windows domain]]** is a set of users and computers managed together in a business organization. **[[Active directory]]** (AD) is a single, centralised repository for administering that network — it's why credentials don't need to exist on every machine, and why a school/work login works on any computer on the network. The **[[Domain Controller]]** is the server running the Active Directory services.

Main advantages of a configured domain:
- **Centralised identity management** — users configured once in AD, usable network-wide
- **Managing security policies** — policies configured centrally and applied to users/computers as needed

---
### Active Directory Domain Service (AD DS)
**AD DS** is the core of any Windows domain — a catalogue of "objects" describing everything on the network. Objects it supports:

- **Users** — security principals that act on network resources; can represent people or services
- **Machines** — created when a computer joins the domain; get their own account (e.g. a machine `TOM-PC` gets the account `TOM-PC$`) and are also treated as security principals
- **[[Security Groups]]** — members automatically inherit the group's privileges (e.g. **Domain Admins** administers all computers/resources in the domain)

**Active Directory Users and Computers** (opened from the Start Menu on the DC) is where **Organizational Units (OUs)** live — a hierarchy of users, computers, and groups sharing the same policy requirements. A user belongs to only one OU at a time.

**OUs vs Security Groups:**
- **OUs** — for **applying policies**
- **Security Groups** — for **granting permissions over resources**

New departments (e.g. a Quality Assurance team) should be grouped into an OU so policies apply consistently to everyone in it.

---
### Managing Users in AD
Reorganising AD to match a target org chart means creating/deleting users and OUs as needed.

⚠️ OUs are protected from accidental deletion by default. To delete one: enable **Advanced Features** in the View menu, open the OU's Properties, and uncheck the deletion-protection box.

**Delegation** grants a specific user control over part of the AD (e.g. one OU) — like the ability to reset passwords in that OU — without making them a full Domain Administrator. Configured via right-click OU → **Delegate Control**, picking the user and the specific task to hand off (e.g. "Reset user passwords and force password change at next logon"). The delegated user can then reset passwords for accounts in that OU, including from PowerShell (`Set-ADAccountPassword` + a forced reset at next logon).

---
### Managing Computers in AD
Every non-DC machine lands in the default **Computers** container. Best practice is to segregate by role into their own OUs:

- **Workstations**
- **Servers**
- **Domain Controllers** (already separated out by Windows)

New OUs are created under the domain root and devices are then moved into the right one. Keeping Servers and Workstations in separate OUs is recommended, since it lets policy be scoped differently to each role.

### Group Policies
A **[[Group Policy Object]]** (GPO) is a collection of settings applied to an OU, managed through **Group Policy Management**. A GPO affects the OU it's linked to and every sub-OU beneath it. Its **Scope** tab shows where it's linked; its **Settings** tab shows the actual configuration (Computer Configuration and/or User Configuration).

GPOs are distributed to domain machines via **SYSVOL**, a network share pointing by default to `C:\Windows\SYSVOL\sysvol\` on each DC; `gpupdate /force` forces an immediate sync.

Two example GPOs:
- **Restrict Control Panel Access** — under User Configuration → Control Panel, enable "Prohibit access to Control Panel and PC settings," then link the GPO to the OUs whose users should be restricted (e.g. Marketing, Management, Sales)
- **Auto Lock Screen** — under Computer Configuration → Policies → Windows Settings → Security Settings → Local Policies → Security Options, set "Interactive logon: Machine inactivity limit" to 300 seconds, then link the GPO to the domain root so it applies everywhere

### Authentication Methods
Two network authentication protocols exist on a Windows domain:

- **[[Kerberos]]** — the default protocol on any recent domain
- **NetNTLM** — legacy, kept only for compatibility; current Windows does not prefer it by default

**Kerberos** is ticket-based:
- **Key Distribution Center (KDC)** — issues tickets on the network
- **Ticket Granting Ticket (TGT)** — lets the user request further Ticket Granting Service (TGS) tickets for specific services
- **Session Key** — issued with the TGT to authenticate follow-up requests
- **krbtgt** — the account whose password hash encrypts the TGT
- **Service Principal Name (SPN)** — identifies the service being accessed; its Service Owner Hash encrypts the TGS ticket

**NetNTLM** is challenge/response, and a password is never transmitted over the network:
1. Client sends an authentication request to the server
2. Server generates a random challenge and sends it to the client
3. Client combines its NTLM password hash with the challenge to compute a response
4. Server forwards the challenge and response to the Domain Controller for verification
5. The DC recalculates the response and compares it; a match authenticates the client
6. Server forwards the result back to the client

### Trees, Forests, and Trusts
- **Tree** — domains joined together because they share the same namespace
- **Forest** — the union of trees with different namespaces into one network. The **Enterprise Admins** group has administrative access over every domain in the forest
- **Trust Relationship** — links domains across trees/forests so a user in one domain can access a resource in another
  - **One-way trust** — the simplest relationship
  - **Two-way trust** — both domains mutually authorise users from the other
