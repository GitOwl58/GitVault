### Transferring files from you host - SCP [[SSH]] 
SCP is short for secure copy, a simple mean of copying files.
It works on a SOURCE and DESTINATION model, allowing:
- Copy files and directories from your system to a remote system.
- Copy files and directories from a remote system to your system.
`scp sourcefile.txt remoteusername@remoteIPaddress:/Path/desired/Newname.txt`
So if i want to send wordlist.txt to my macbook called fred, on his desktop and call it hydralist :
`scp wordlist.txt fred@194.152.1.100:/Users/fred/Desktop hydralist.txt`
And to do the opposite:
`scp fred@194.152.1.100:/Users/fred/Desktop/hydralist.txt wordlist.txt`

### Processes 101
Processes are the programs that are running on your machine, managed by the kernel, where each process has an ID associated with it, called [[PID]]. 
The PID's order is the one in which the process starts, the 5'th process will have a PID of 5.
You can run `ps`, providing a list of the running processes on your user's session, and some additional info such as status code, session running it, usage time and CPU use, with the name of program or command executed.
To see process run by other users, and those that don't run from a session (system processes), you need to provide aux, `ps aux`.
Another useful command is `top` or `htop` if it's installed, updating processes every few seconds.
### Managing processes
You can run commands terminating processes, to kill a command you can use `kill` associated with the PID, `kill 1337`.
Some signals that can be sent to processes when killed:
- SIGTERM: Kill the process but allows it to cleanup tasks beforehand.
- SIGKILL: Kill, doesn't cleanunp after.
- SIGSTOP: Stop, suspend process.
### How process start
Namespaces. OS uses namespaces to split up available resources (CPU/RAM/Priority).
Like a cake, splitting computer in slices, processes within that slice will have access to a defined amount of computing power.
Namespaces are great for security, isolating processes from another, only processes in the same namespace will see each other.
The process with [[PID]] 0 is a process started during boot, it is the system's init on Ubuntu, such as [[systemd]], used to provice a way to manage user's processes, sitting between the OS and the user.
Systemd (PID 1) is the first process started on boot. All other processes start as **child processes** of systemd — controlled by it but running independently with their own PID, sharing systemd's resources.
### Getting Processes/Services to start on boot
Some applications can be started on boot; Web servers, database servers, file transfer servers.
`systemctl`, this command allows to interact with systemd process/daemon, the format is `systemctl option service`, example:
`systemctl start apache2`, telling apache to start up.
We can do five options with `systemctl`:
- `start`
- `stop`
- `enable`
- `disable`
- `status`
### Introduction to backgrounding and foregrounding in [[Linux]]
**Foreground vs Background processes:**

Every process runs in one of two states:

**Foreground** — the process has control of your terminal. You see its output, you can interact with it, but you can't type other commands until it finishes. Most commands run this way by default (`echo`, `ping`, scripts etc.).

**Background** — the process runs silently behind the scenes, freeing your terminal immediately so you can keep working. Two ways to do it:

- Add `&` at the end of a command **before** running it → runs in background from the start, returns the PID
- Press **Ctrl+Z** on a already-running process → pauses/suspends it and pushes it to background mid-execution

**`fg`** — brings a backgrounded process back to the foreground so you can interact with it again.

**Real example you've already used today:**

bash

```bash
plasmashell &
```

You ran plasmashell in the background so your terminal stayed free — exactly this concept in practice. And when you closed the terminal and plasmashell died, that's because the background process was still a child of that terminal session.

**`disown`** (which you also used) goes one step further — completely detaches the process from the terminal so it survives even if the terminal closes.
### Automation
**Cron** is a system process started at boot, responsible for managing and executing scheduled tasks called **cron jobs**. Tasks are defined in a **crontab** — a special file with a specific formatting that cron reads and executes line by line.

**Crontab structure — 6 fields:**

```
MIN   HOUR   DOM   MON   DOW   CMD
```

- **MIN** — minute (0-59)
- **HOUR** — hour (0-23)
- **DOM** — day of month (1-31)
- **MON** — month (1-12)
- **DOW** — day of week (0-6, Sunday=0)
- **CMD** — the actual command to run

**Example — backup Documents every 12 hours:**

```
0 */12 * * * cp -R /home/user/Documents /var/backups/
```

**Wildcard `*`** — means "every" / "don't care about this field". `*/12` means "every 12 intervals".

**Special shorthands:**

```
@reboot   → run once on boot
@daily    → run once a day  
@hourly   → run once an hour
@weekly   → run once a week
```

**Edit your crontab:**

bash

```bash
crontab -e
```

Opens in your default editor (nano, vim etc.) — each line is one scheduled job.

**Useful tools for generating crontab syntax:**

- crontab.guru — paste your cron expression and it explains it in plain English
- Crontab Generator — GUI to build expressions visually
### **Packages & Software Repositories**

Software is distributed through **repositories** — trusted registries maintained by OS vendors or the community. On Ubuntu, `apt` is the package manager that handles installing, updating, and removing software by pulling from these repositories.

#### **Why repositories matter:**

- Software integrity is guaranteed via **GPG keys** — cryptographic signatures from developers proving the software is legitimate and untampered
- When you run `apt update`, all added repositories are checked for updates automatically — no manual tracking needed

---

**Adding a third-party repository (Sublime Text example):**

#### **1. Download and trust the GPG key:**

bash

```bash
wget -qO - https://download.sublimetext.com/sublimehq-pub.gpg | sudo apt-key add -
```

**2. Create a dedicated source file** (best practice — one file per third-party repo):

bash

```bash
sudo nano /etc/apt/sources.list.d/sublime-text.list
```

Add the repository URL inside, save and exit.

**3. Update apt to recognize the new repo:**

bash

```bash
sudo apt update
```

**4. Install the software:**

bash

```bash
sudo apt install sublime-text
```

---

**Removing a package and its repository:**

bash

```bash
sudo add-apt-repository --remove ppa:PPA_Name/ppa
# or manually delete the .list file from /etc/apt/sources.list.d/
sudo apt remove sublime-text
```
### Managing logs
**Log Files**

Logs are stored in `/var/log/` — files and folders containing records of activity from applications, services, and the OS itself. Linux automatically manages log rotation (archiving/deleting old logs) to prevent disk saturation.

---

**Key services with notable logs:**

|Service|Purpose|
|---|---|
|**Apache2**|Web server — every HTTP request logged|
|**fail2ban**|Monitors and blocks brute force attempts|
|**UFW**|Firewall activity and blocked connections|

---

**Web server log types:**

- **access.log** — every request made to the server (IP, timestamp, URL, response code)
- **error.log** — failed requests, misconfigurations, server errors

---

**Other important logs:**

- **Authentication attempts** — successful/failed logins (`/var/log/auth.log`)
- **OS activity** — system events, kernel messages (`/var/log/syslog`)

---

**Why logs matter:**

- Monitor system health
- Detect intrusions or brute force attempts
- Diagnose performance issues
- Forensic investigation after an incident
