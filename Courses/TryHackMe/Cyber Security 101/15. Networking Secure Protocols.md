### [[TLS]]
Netscape's SSL (1995) evolved into the IETF's **[[TLS]]** (1999), now at TLS 1.3 (2018). TLS sits at the OSI transport layer and wraps an existing protocol to add **confidentiality** (no one can read the data), **integrity** (no one can alter it), and **authenticity** (you're really talking to the right server): the appended "S" (HTTPS, SMTPS, DoT, MQTTS...) signals TLS underneath.

A server proves its identity with a **[[Certificate]]**: the administrator submits a Certificate Signing Request to a Certificate Authority, who verifies it and signs a certificate the client can validate against its trusted CA store (or, for free, via Let's Encrypt). A **self-signed certificate** skips the CA: no third party has confirmed it, so it can't prove authenticity.

### [[HTTP|HTTPS]]: HTTP Over TLS
Plain HTTP (port 80) is sent in cleartext, so anyone capturing traffic reads it as-is. **HTTPS** (port 443) inserts a TLS session between the TCP handshake and the HTTP request: TCP handshake → TLS negotiation → HTTP over the encrypted channel. Captured HTTPS traffic just shows as "Application Data": gibberish without the session's decryption key.

---
### SMTPS, POP3S, IMAPS
Adding TLS to [[SMTP]], [[POP3]], and [[IMAP]] works exactly like HTTPS: same TCP handshake → TLS → protocol pattern, just on different ports.

| Protocol | Plaintext port | Secure port |
| -------- | --------------- | ----------- |
| HTTP     | 80               | 443 (HTTPS) |
| SMTP     | 25               | 465 / 587 (SMTPS) |
| POP3     | 110              | 995 (POP3S) |
| IMAP     | 143              | 993 (IMAPS) |

### [[SSH]]: Replacing Telnet
Tatu Ylönen released SSH-1 in 1995 (the same year as SSL) to replace cleartext [[Telnet]] for remote administration; SSH-2 followed in 1996, and OpenSSH (1999, OpenBSD) is the open-source implementation nearly every SSH client is built on today. TELNET listens on port 23, SSH on **port 22**.

Beyond password login, SSH supports **public-key** and two-factor authentication, warns of unrecognised server keys (anti-MITM), protects the integrity of exchanged data, and can **tunnel** other protocols through it (VPN-like) or forward a remote GUI app over the network (**X11 forwarding**, e.g. `ssh host -X`).

---
### [[SFTP]] and [[FTPS]]
Two different ways to secure [[FTP]], easy to mix up:
- **SFTP** (SSH File Transfer Protocol) rides on the SSH protocol suite, shares its port 22, and uses Unix-like `get`/`put` commands. Just an option to enable on an OpenSSH server.
- **FTPS** (FTP Secure) is FTP wrapped in TLS instead: needs its own certificate, uses port 990, and is trickier through strict firewalls since control and data still use separate connections.

---
### [[VPN]]
A Virtual Private Network builds an encrypted tunnel over the (inherently unencrypted) Internet so that remote branches or individual users can reach a private network as if physically on-site. Once the tunnel is up, all traffic usually routes through it: the outside world sees the VPN server's IP, not the client's, which is also how VPNs bypass geographic restrictions. Some VPNs only route access to the private network without tunneling all traffic, and some leak the real IP despite promising otherwise. Using a VPN is illegal in some countries, so it's worth checking local regulations, especially while travelling.
