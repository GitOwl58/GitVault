### [[Nmap]]

Open-source network scanner, first published in 1997. Answers two core questions: which hosts on a network are alive, and which network services (SSH, web servers, etc.) are listening on them. Doing this manually with `ping`, `arp-scan`, or one-by-one `telnet` attempts doesn't scale, `ping` gives nothing if the target's firewall blocks ICMP, `arp-scan` only works on the same local network, and probing 65,535 ports by hand is a non-starter. Nmap is almost always run as root/`sudo`, since a non-root user is limited to basic scan types (ICMP echo, TCP connect).

  

**Target specification:** an IP range with `-` (`192.168.0.1-10`), a subnet with `/` (`192.168.0.1/24`, equivalent to `.0`-`.255`), or a hostname (`example.thm`).

  

---

### Host Discovery

**Local network** (directly connected via Ethernet/Wi-Fi): `nmap -sn 192.168.66.0/24` sends [[ARP]] requests; any device that replies gets marked "Host is up". Because the traffic is local, Nmap can also read each device's [[MAC address]] and guess its vendor from it, useful context on what kind of device it is.

```

nmap -sn 192.168.66.0/24

Nmap scan report for XiaoQiang (192.168.66.1)

Host is up (0.0069s latency).

MAC Address: 44:DF:65:D8:FE:6C (Unknown)

[...]

Nmap done: 256 IP addresses (7 hosts up) scanned in 2.64 seconds

```

  

**Remote network** (at least one router/hop away): ARP won't reach across a router, so Nmap falls back to a mix of ICMP echo requests, ICMP timestamp requests, TCP SYN probes to port 443, and TCP ACK probes to port 80, any single reply marks the host as up. A host that ignores all of them (or sits behind a firewall dropping everything) shows as down, which is why remote host discovery is inherently less reliable than local ARP-based discovery.

```

nmap -sn 192.168.11.0/24

Nmap scan report for 192.168.11.1

Host is up (0.018s latency).

[...]

Nmap done: 256 IP addresses (5 hosts up) scanned in 10.67 seconds

```

  

`-sn` only discovers live hosts, it never touches ports, so it's the quieter option when the goal is just mapping who's on the network.

### Port Scanning

**[[Port Scan]]**: with up to 65,535 TCP ports and the same for UDP per host, checking each one by hand (e.g. via `telnet`) doesn't scale either.

  

**TCP Connect Scan** (`-sT`, see **[[TCP Connect Scan]]**): completes the full [[Three-way handshake]] with every target port. An open port completes the handshake and gets torn down by Nmap with a TCP RST-ACK; a closed port replies RST-ACK immediately, without ever completing it. This is the same thing a `telnet` client does, just automated and exhaustive.

![[Wireshark TCP connect scan open port.png|500]]

  

**SYN Scan** (`-sS`, "stealth scan", see **[[SYN Scan]]**): sends only the initial SYN. An open port replies SYN-ACK, but instead of completing the handshake, Nmap responds with RST, the connection is never actually established. Fewer logs get written server-side as a result, making this the quieter default choice; it requires raw-socket access (root).

![[Wireshark SYN stealth scan open port.png|500]]

  

**UDP Scan** (`-sU`, see **[[UDP Scan]]**): [[UDP]] has no handshake to complete, so Nmap just sends a probe; a closed port typically answers with an [[ICMP]] "Destination Unreachable (port unreachable)", while an open one often stays silent, since UDP has no obligation to acknowledge anything. That ambiguity makes UDP scans slower and less certain than TCP ones. Common UDP services worth checking for: DNS, DHCP, NTP, SNMP, VoIP.

![[Wireshark UDP scan destination unreachable.png|500]]

  

**Limiting target ports:** Nmap scans the 1000 most common ports by default. `-F` narrows that to the 100 most common (fast mode); `-p[range]` sets an explicit range, e.g. `-p10-1024`, `-p-25` (1-25), or `-p-` for all 65,535 ports (`-p1-65535`). `-p1-1023` targets just the well-known ports.

  

**Cheatsheet:**

  

| Option | Explanation |

|---|---|

| `-sT` | TCP connect scan, completes the three-way handshake |

| `-sS` | TCP SYN scan, only the first step of the handshake |

| `-sU` | UDP scan |

| `-F` | Fast mode, scans the 100 most common ports |

| `-p[range]` | Specific port range; `-p-` scans all 65,535 |

### Version and OS Detection

**OS Detection** (`-O`): guesses the target's OS from various indicators (TCP/IP stack quirks, response behaviour). Not exact, e.g. reporting "Linux 4.X\|5.X" for a host actually running 5.15, close but not precise.

```

nmap -sS -O 192.168.124.211

PORT STATE SERVICE

22/tcp open ssh

Device type: general purpose

Running: Linux 4.X|5.X

OS details: Linux 4.15 - 5.8

```

  

**Service/Version Detection** (`-sV`): adds a VERSION column identifying exactly what's listening, e.g. the specific OpenSSH build and OS.

```

nmap -sS -sV 192.168.124.211

PORT STATE SERVICE VERSION

22/tcp open ssh OpenSSH 8.9p1 Ubuntu 3ubuntu0.10 (Ubuntu Linux; protocol 2.0)

```

  

`-A` bundles OS detection, version detection, and traceroute into one flag. `-Pn` forces Nmap to treat every host as up and port-scan it anyway, useful when a target doesn't respond during host discovery but might still have open ports (e.g. it's just ignoring ICMP). `-sL` lists the targets a scan *would* hit without actually scanning them, handy for sanity-checking a range before firing it off. `-PS[portlist]`, `-PA[portlist]`, `-PU[portlist]` give finer control over which ports are used for TCP SYN/ACK and UDP host-discovery probes.

  

**Cheatsheet:**

  

| Option | Explanation |

|---|---|

| `-O` | OS detection |

| `-sV` | Service and version detection |

| `-A` | OS detection + version detection + traceroute, etc. |

| `-Pn` | Treat all hosts as up, scan regardless |

| `-sL` | List scan, targets only, no actual scanning |

### Timing: How Fast is Fast

See **[[Nmap Timing Templates]]**: a loud, fast scan risks tripping an **[[IDS]]** or other defenses, so Nmap offers six named/numbered speed presets, from `-T0`/paranoid (slowest, most spread out) to `-T5`/insane (fastest, most likely to get noticed): paranoid (0), sneaky (1), polite (2), normal (3), aggressive (4), insane (5). Scanning the same 100 ports with each template showed a dramatic spread, from 9.8 hours at T0 down to 0.13 seconds at T4.

  

At T0, Nmap waited roughly 5 minutes between each port probe:

![[Wireshark T0 timing scan interval.png|500]]

By T3 (the default), the gaps are essentially gone, Nmap fires as fast as the connection allows:

![[Wireshark T3 timing scan interval.png|500]]

  

Beyond the timing templates: `--min-parallelism`/`--max-parallelism` bound how many probes run simultaneously per host group (Nmap normally adjusts this automatically based on network reliability); `--min-rate`/`--max-rate` bound the packets-per-second rate for the whole scan, not per host; `--host-timeout` caps how long Nmap will wait on a single slow host before giving up on it.

  

**Cheatsheet:**

  

| Option | Explanation |

|---|---|

| `-T<0-5>` | Timing template: paranoid/sneaky/polite/normal/aggressive/insane |

| `--min-parallelism`/`--max-parallelism` | Bound simultaneous probes |

| `--min-rate`/`--max-rate` | Bound packets/second, scan-wide |

| `--host-timeout` | Max time to wait on one host |

### Output: Controlling What You See

**Verbosity/debugging:** `-v` shows real-time progress (ARP ping scan → parallel DNS resolution → SYN stealth scan per host, etc.), stackable (`-vv`, `-vvvv`) or settable directly (`-v2`, `-v4`); pressing "v" mid-scan bumps it live too. `-d` gives debugging-level output, same stacking logic, up to `-d9` (extremely verbose).

  

**Saving reports:** three main formats, `-oN <file>` (normal, human-readable), `-oX <file>` (XML), `-oG <file>` (grepable, for `grep`/`awk`). `-oA <basename>` writes all three at once.

```

nmap -sS 192.168.139.1 -oA gateway

# ls

gateway.gnmap gateway.nmap gateway.xml

```

  

**Cheatsheet:**

  

| Option | Explanation |

|---|---|

| `-v` / `-vv` / `-d` | Increasing verbosity / debug output |

| `-oN <file>` | Normal (human-readable) output |

| `-oX <file>` | XML output |

| `-oG <file>` | Grepable output |

| `-oA <basename>` | All three formats at once |
